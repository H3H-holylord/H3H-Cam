# Стабильность камеры во время игры

Windows 4.0.7, Android 4.0.3. Настройки разрешения, FPS, кодека, битрейта и эффектов сохраняются.

## Что изменено

- Обработка основного видеовывода выполняется в отдельном потоке, зарегистрированном в MMCSS Capture с приоритетом HIGH. Если MMCSS недоступен, остаётся обычный приоритет потока AboveNormal. При завершении регистрация снимается на том же потоке. Клиент и FFmpeg сохраняют приоритет процесса AboveNormal.
- Предпросмотр масштабирует кадры и вызывает обработчик интерфейса в отдельном потоке BelowNormal. У него два повторно используемых буфера и только один заменяемый ожидающий кадр. Медленный обработчик снижает FPS предпросмотра, но не задерживает основной вывод. Скрытый предпросмотр не копирует и не масштабирует кадры.
- Spout допускает не более двух незавершённых загрузок кадра в GPU. Готовность проверяется через D3D11 event queries без ожидания завершения. Если очередь занята, текущий кадр пропускается; следующая попытка использует свежий кадр. Счётчик `GPU skipped` отображается в диагностической строке. Это ограничение очереди клиента, а не резервирование ресурсов GPU.
- Когда источник продолжает передавать видео, но основной вывод более трёх секунд не публикует кадры, монитор заменяет декодер и запрашивает IDR. При запуске нового вывода действует восемь секунд на прогрев. Режим приватности не вызывает такое восстановление.

Очередь готовых raw-кадров остаётся ограниченной одним ожидающим кадром и тремя буферами. При перегрузке клиент заменяет устаревший кадр вместо накопления задержки.

MMCSS и получение статуса GPU описаны в документации Microsoft: [MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service), [ID3D11DeviceContext::GetData](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-getdata).

## Проверка 2026-10-04

Локальный ПК: 16 логических процессоров, RTX 4070 Ti. Samsung Note9, USB ADB, 1920×1080, 60 FPS, HEVC 32 Мбит/с, Clean, Spout и виртуальная камера. OBS открыт, без эфира/записи. Это синтетическая нагрузка; Hunt не запускался.

Тест создаёт конкуренцию за CPU отдельными работниками и за GPU отдельным D3D11 compute-процессом. Нагрузка ограничена двадцатью секундами; команды GPU подаются ограниченными пакетами. Используются фактические системные счётчики CPU и `nvidia-smi`, а не заявленный процент нагрузки помощников.

Дополнительно обработчик предпросмотра намеренно задержан на 80 мс при каждом кадре. В такой конфигурации предпросмотр выдаёт около 11 FPS, а основной вывод проверяется независимо. FPS Spout означает число принятых клиентом загрузок, FPS виртуальной камеры — число публикаций в общей памяти. Это не измерение FPS рендера OBS или задержки «объектив → монитор».

Первый замер с тяжёлой нагрузкой: **60,04 FPS** в обоих выходах при среднем **80,3% CPU / 89,2% GPU**, `GPU skipped = 0`, ошибок декодирования 0. После снятия нагрузки — 59,97 FPS. Зависший в отдельном тесте FFmpeg был автоматически заменён; новые кадры появились за **6,63 секунды**.

Итоговый повтор с измерением интервалов публикации основного вывода:

| Этап | FPS виртуальной камеры / Spout | CPU / GPU | P99 интервала вывода | Максимальный интервал |
|---|---:|---:|---:|---:|
| До нагрузки | 59,94 / 59,94 | 22,8% / 40,2% | 21,57 мс | 32,93 мс |
| Совместная нагрузка, 14 секунд | **60,02 / 60,02** | **80,0% / 89,5%** | **19,65 мс** | **27,36 мс** |
| После нагрузки | 60,04 / 60,04 | 23,9% / 26,7% | 19,99 мс | 21,27 мс |

`GPU skipped = 0`, ошибок декодирования 0 на всех этапах. P99 — интервал, который не превышают 99% пар последовательных публикаций; это не полная задержка камеры. Проценты CPU/GPU относятся ко всему ПК, включая нагрузочные процессы и фоновые приложения.

Аппаратная проверка также подтверждает скрытие/возобновление предпросмотра, переключения выходов, резервный декодер NV12, поворот 90° и завершение процессов. Тесты буферов проверяют, что занятый кадр не перезаписывается, а ожидающий кадр заменяется последним.

## Повторить тест

Закройте рабочий H3H Cam и автоматический помощник, который может его перезапускать. Подключите телефон по USB ADB. Команды запускают камеру и возвращают сохранённые настройки при завершении:

```powershell
dotnet run --project tests -c Release -- unit test-results
dotnet run --project tests -c Release -- shared-preview-test
dotnet run --project tests -c Release -- watchdog-test
dotnet run --project tests -c Release -- stress-test test-results/game-load 60 80
```

Последняя команда длится около минуты: прогрев, обычный режим, совместная нагрузка и восстановление. Отчёт `stress.json` содержит фактические FPS, интервалы публикации основного вывода/предпросмотра и загрузку. Проверки успешны, если каждый этап даёт хотя бы 95% заданных FPS в обоих выходах, P99 основного интервала не выше 100 мс, максимальный интервал не выше 250 мс и нет ошибок декодирования. На другом устройстве неподдерживаемый режим или недостаточные ресурсы приведут к неуспешному тесту.

## Во время Hunt

Для OBS используйте Spout2 Capture. Выключайте ненужный предпросмотр либо сворачивайте клиент; AI-фон и 4K-апскейл включайте только при необходимости. Если видеокарта постоянно занята полностью, ограничьте FPS игры, чтобы осталось время для камеры и OBS. Это соответствует [рекомендации OBS при перегрузке GPU](https://obsproject.com/kb/encoding-performance-troubleshooting).

Приоритет и короткие очереди уменьшают риск отставания, но не гарантируют 60 FPS при любой загрузке. Полный путь аппаратного декодирования с D3D11-текстурами ещё не реализован: текущий FFmpeg передаёт raw-пиксели через системную память. Общая архитектура и измерения CPU описаны в [PERFORMANCE.md](PERFORMANCE.md).
